## 1. Checksum DB — correctif appliqué

### 1.1 Diagnostic confirmé

Le fichier `ministere.duckdb.gz.sha256` de la release **v0.5-economie-legislatif** a pu être lu depuis ce conteneur :

```
a43e50d68911d85e46fcf7ec29310723090609bc07e4ce8d78b7ba4dd1def492  data/ministere.duckdb.gz
```

C'est l'empreinte de l'**archive compressée** : elle est identique au digest GitHub de l'asset `.gz`. Le chemin `data/…` indique une génération manuelle par `shasum` depuis la racine du dépôt, et non par `publish_db.sh`, qui écrit un chemin absolu.
`deploy/update.sh` la comparait au SHA256 de la base **décompressée**. Les deux valeurs ne pouvaient jamais correspondre : **chaque `update.sh` retéléchargeait les ~635 Mo**. Le constat §3.3 est confirmé.

Autres défauts corrigés au passage :

- `install.sh` ne vérifiait aucune empreinte.
- `update.sh` passait par `/tmp`, sans contrôle d'intégrité. Il arrêtait l'application **avant** de savoir si l'archive était valide.
- `install.sh`/`update.sh` utilisaient `releases/latest`. Une release de code sans DB (cas prévu par le README) rendait donc la base introuvable.
- `download_db.sh` ne cherchait que les tags `db-*`. Sans argument, il aurait pris **db-2026-05** (mai) au lieu de v0.5.
- `publish_db.sh` écrivait un chemin absolu dans le `.sha256` et produisait une archive non reproductible (nom et date dans l'en-tête gzip). Il proposait aussi `gh release create db-YYYY-MM`, alors que la pratique réelle est d'attacher la base à la release `v*`.

### 1.2 Convention retenue

| Élément | Contenu |
|---|---|
| `ministere.duckdb.gz` | Base compressée, `gzip -n` (reproductible) |
| `ministere.duckdb.gz.sha256` | SHA256 **de l'archive**, format `<hash>  ministere.duckdb.gz` |
| `~/.ministere-info/db-release.state` (poste utilisateur) | Tag, empreinte publiée, SHA256 archive, SHA256 base, date |

Pourquoi l'archive plutôt que la base :

- c'est le format de la release v0.5 existante ;
- il coïncide avec le digest natif que GitHub affiche pour chaque asset ;
- il se vérifie avant décompression ;
- `shasum -c` fonctionne tel quel.

**Rétrocompatibilité** : les clients ne lisent que le premier champ, donc un chemin éventuel est ignoré. Ils acceptent aussi une empreinte égale au SHA256 de la base décompressée (ancienne variante du README). Les deux méthodes de publication restent donc installables.

**Logique de `update.sh`** :

1. Il cherche la release la plus récente qui contient `ministere.duckdb.gz`.
2. Il lit l'empreinte publiée.
3. Il la compare à `DB_REMOTE_SHA256` de l'état local, sans re-hacher 1 Go.
4. Sans état (installations antérieures), il compare au SHA256 de la base locale. Pour v0.5 (empreinte d'archive), cela provoque **un unique retéléchargement**, inévitable car l'archive n'est pas reconstructible à l'identique. L'état est ensuite écrit et les passages suivants ne retéléchargent plus.
5. Le téléchargement se fait dans `~/.ministere-info/.telechargement.XXXXXX`, sur le même disque, suivi de `gzip -t`, de la décompression et de la vérification de l'empreinte (archive ou base). Ce n'est **qu'ensuite** que viennent `docker compose stop`, `mv` et l'écriture de l'état.
6. En cas d'échec, la base en place, l'état et l'application sont intacts, et le dossier temporaire est supprimé (trap EXIT).

`install.sh` suit le même parcours et écrit l'état initial. Il s'interrompt si l'empreinte est absente ou invalide.

Le bloc de fonctions est **dupliqué à l'identique** dans `install.sh` et `update.sh`. Ces scripts sont exécutés via `curl | bash` et ne peuvent pas sourcer une bibliothèque. Les marqueurs `Synchronisation de la base` et `Fin du bloc synchronisé` délimitent le bloc, et un `diff` entre les deux fichiers le vérifie.

## 2. Dockerfiles

### 2.1 Appliqué : uv figé

`deploy/Dockerfile` : `ghcr.io/astral-sh/uv:latest` → `ghcr.io/astral-sh/uv:0.11.16`, comme le Dockerfile racine et conformément à `docs/lessons-learned.md` l. 51. Aucun autre changement.

### 2.2 Constats supplémentaires

1. **`.streamlit/config.toml` absent des deux images.** Ce fichier contient `theme.base = "light"`, `primaryColor = "#000091"`, etc. Le compose dev le monte en volume, mais ni `deploy/Dockerfile` ni `Dockerfile` ne le copient. L'image GHCR tourne donc **sans la configuration de thème** : sur un Mac en mode sombre, Streamlit peut basculer en thème sombre, sous le CSS du design system. C'est à corriger dans l'image unifiée.
2. `deploy/Dockerfile` lance `uv run streamlit …` à l'exécution. `uv run` vérifie et peut resynchroniser l'environnement au démarrage, ce qui peut exiger le réseau. Il vaut mieux lancer directement le binaire du venv.
3. `deploy/docker-compose.yml` monte la base en **lecture-écriture**. Or l'application n'ouvre DuckDB qu'en `read_only=True` (`viz/*_queries.py`, `pages/1_📍_Géographie.py`), et seul `update.sh` écrit, depuis l'hôte et conteneur arrêté. Un montage `read_only: true` est possible.
4. Chemins `Path(__file__).resolve().parents[3] / "data"` (`viz/*_queries.py`, `etl/_common.py`, `data_sources/*`) : ils ne donnent `/app/data` que si le paquet est installé en **mode éditable** depuis `/app/src`, ce qui est le défaut de `uv sync`. Une installation non éditable (`--no-editable`) ou une copie du venv sans `/app/src` ferait pointer vers `site-packages/../data`.
5. Tectonic (racine) : environ 50 Mo et un téléchargement GitHub au build, pour une fonctionnalité non implémentée (rapports PDF).
6. `libgdal-dev`/`libgdal32` (racine) : probablement inutiles, car les wheels `pyogrio`/`shapely` embarquent GDAL/GEOS. C'est à vérifier avant de les retirer.

- `.github/workflows/docker-publish.yml` : `file: deploy/Dockerfile` → `file: Dockerfile`.
- `deploy/docker-compose.yml` : montage `read_only: true` et `start_period` inchangé.
- Supprimer `deploy/Dockerfile`.
- Mettre à jour `docs/deployment.md` et `docs/architecture.md`.

**Risques :**

1. **Permissions du bind mount (non-root)** : `~/.ministere-info/data` appartient à l'utilisateur macOS (uid 501), et le conteneur tourne en uid 1000. Avec OrbStack, les fichiers d'un bind mount sont en pratique accessibles : le partage de fichiers réassigne la propriété. Et la base est en `0644` (créée par `gunzip -c >`), donc lisible par tous. L'application ne fait que lire en `read_only=True`, sans WAL. **Risque faible, mais à valider sur le Mac** (`docker exec ministere-info ls -ln /app/data`). En cas d'échec : `user: "${UID}:${GID}"` dans le compose ou retour temporaire à root.
2. **Extension spatial** : si l'image tourne avec un autre uid (`user:` dans le compose), `~/.duckdb` de `app` n'est plus le HOME. `LOAD spatial` échouerait alors : l'extension ne serait pas trouvée, et son installation automatique demanderait le réseau. Parade : fixer le répertoire d'extensions côté code (`SET extension_directory = '/opt/duckdb_extensions'`, dans src/) et l'installer à cet emplacement au build. Sinon, garder `USER app` sans surcharge dans le compose.
3. **parents[3]** : il repose sur l'installation éditable. L'assertion au build le verrouille. Ne jamais ajouter `--no-editable`.
4. **Retrait de GDAL système** : si une dépendance compile depuis les sources sur arm64 (aucune wheel disponible), le build échoue. C'est détectable immédiatement en CI multi-arch. Sinon, garder `libgdal32`.
5. **Dev compose** : il continue de monter `./src`, `./pages`, `./app.py` et `./.streamlit` en volumes. L'image copie `.streamlit`, et le montage le remplace sans conflit. En dev, `runOnSave` : le compose dev définit déjà `STREAMLIT_SERVER_RUN_ON_SAVE=true`, qui l'emporte sur l'ENV de l'image.
6. **Taille/temps de build** : sans Tectonic ni GDAL, l'image rétrécit (environ −80 à −150 Mo, estimation). Le build QEMU arm64 passe par le cache uv (`--mount=type=cache`, BuildKit, disponible sur GHA buildx et OrbStack).

## 3. CI — propositions (NON appliquées)

### 3.1 Déclencheur

État actuel : `push` sur `main` et `pull_request` vers `main` uniquement. Un push sur `claude/**` ne déclenche rien.

Option A, branches Claude uniquement :

```yaml
on:
  push:
    branches: [main, "claude/**"]
  pull_request:
    branches: [main]
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Option B, toutes les branches (recommandée : couvre aussi les branches `feat/…` prévues par la convention « branche par feature ») :

```yaml
on:
  push:
    branches: ["**"]
    tags-ignore: ["**"]      # les tags v* sont déjà traités par docker-publish.yml
  pull_request:
    branches: [main]
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Avec une PR ouverte, un push déclenche deux runs (`push` et `pull_request`). Le groupe `concurrency` par `ref` ne les fusionne pas, car leurs refs diffèrent. C'est acceptable (environ 2 × 2 min). On peut aussi n'exécuter `pull_request` que pour les forks.

### 3.3 Proposition de marqueur

    "slow: ...",

| Option | CI par défaut | Conséquence |
|---|---|---|
